# S-WEB: the Control Center canvas in a real WKWebView (WP-03)

Date 2026-10-04. Machine: one Apple silicon Mac (arm64), macOS 27, Xcode 27, Swift 6.x. One machine, one OS build.
Code and evidence: `spikes-tracked/web/` (SwiftPM, AppKit + WKWebView, no SwiftUI, no macros). Build outputs are git-ignored.

The build plan this spike tested is an internal planning document and is not published; where this note quotes it, the quote is the plan's wording at the time. The `spikes-tracked/` code and raw evidence, and the commits this note mentions, stayed in the development tree and are not published either.

## Verdict

**S-WEB passes. The plan's canvas design works as written; the fallback ("a single file + a sha256 CSP hash") is not needed.**

- A `WKURLSchemeHandler` on `wasitme-app:` serves separate `app.html`, `app.js`, `app.css`, a font and images. The plan's exact CSP is sent as an HTTP header on every response (no meta tag). The page renders, scripts and styles run, and nothing leaves the web view.
- Data goes in only through `callAsyncJavaScript(arguments:)`. A JS-set DOM marker rendered, and an offscreen `takeSnapshot` PNG shows it (`spikes-tracked/web/evidence/matrix/snapshot-hidden.png`; 2048x1636 px, 255,840 green marker pixels that exist only if JS set an attribute and the external stylesheet applied).
- The plan's performance budget "Control Center open, app + WebContent ≤ 180 MB" **passes at steady state** (112 MiB RSS for the default page, 122 for 90 days, 151 for the heaviest page tested). It **fails during a `takeSnapshot` on tall pages** (238 to 268 MiB). That is a QA-only path.
- Two findings change the plan and need a decision (below): a dictionary argument containing a `__proto__` key replaces that object's prototype, and the app does not return to its pre-WebKit memory after the canvas closes.

Everything below was re-run on the final code and binary today. Where a number comes from a single run it says so.

## Corrections to the salvaged work

The previous (stopped) agent left a working harness and evidence but no write-up. Re-verifying it found two defects, both fixed:

1. **The external memory observer never saw the WebContent or Networking processes.** The harness returned from `SpikeRunner.run` before holding, which released the `WKWebView`; its helpers exit within a second, so `ps`/`footprint` listed only the app and the shared GPU process. The salvaged `ps-`/`footprint-` files only ever listed the app and GPU process, so the WebContent and Networking numbers had been seen in-process only. Fixed with a `beforeRelease` hook that keeps the web view alive through the hold. All four processes are now observed externally, and external `ps` agrees with the in-process sampler to within 0.4 MiB (app + WebContent, settled: ps 112.2, in-process 112.2).
2. `SpikeRunner` leaked a `wasitme-spike-rules-<pid>` temp directory per rules run. Now removed on return (0 left after the full test run).

Also: the salvaged "days90 / days365-heavy are over budget" numbers were taken right after a snapshot. Steady state is much lower (see Memory). The old evidence was replaced by evidence from the final binary (3 PNGs reduced to 1; per-run report JSONs reduced to a summary).

It does not prove nothing else on the machine was contacted by WebKit's Networking process for its own reasons; the plan's claim ("no networking code of ours; WebKit navigation is denied") is the right wording.

### Data in: what crosses `callAsyncJavaScript(arguments:)`

| Value | Arrives as |
|---|---|
| int, double, bool, nested dict, `NSNull`, `""`, `[]` | the same JS types (`NSNull` becomes `null`) |
| string with `</script>`, quotes, backtick, `${}`, backslashes, U+2028/2029, bidi override, ZWJ, astral emoji | identical UTF-16 units, and identical text read back from `textContent` |
| string containing NUL | length preserved |
| int64 above 2^53 (`2^53+1`) | rounded to `2^53` (JS number) |
| `NaN`, `±Infinity`, `Date` | `NaN`, `Infinity`, a JS `Date` (they do not go through JSON) |
| **dict key `"__proto__"`** | **replaces that object's prototype** (the object then inherits `polluted`); the global `{}` stayed clean |
| the same hostile object as ONE JSON string parsed with `JSON.parse` in the page | **safe**: own property `__proto__`, prototype not replaced, no global pollution |

The `__proto__` finding matters because the keys of the real payload include names that come from users' logs (tool, MCP-server, model and project names). Caution for the page code: copying a parsed object with `Object.assign` uses `[[Set]]` and can re-trigger the setter; use `structuredClone`, spread, or `Map`/`Object.hasOwn`. Not tested here (spike page does not copy parsed data).

### Memory

Definitions: RSS is resident set size (what `ps` shows, and the unit the plan's performance budgets use: "App idle 45–50 MB RSS"). Footprint is `phys_footprint` from `footprint -f bytes` (closest to Activity Monitor's Memory column; it excludes shared framework pages, so it is much smaller). 1 MiB = 1,048,576 bytes. External = `ps` and `footprint` run from outside against the same live pids; in-process = `proc_pid_rusage` inside the app. The WebContent pid is attributed with the `_webProcessIdentifier` SPI (measurement only, never ships).

Steady state (settled 3 s, no snapshot), medians; WebContent = the one web process, Net = Networking helper, GPU = shared GPU helper:

| Page | Runs | app+WebContent RSS | app+WebContent footprint | all 4 processes RSS | all 4 footprint |
|---|---|---|---|---|---|
| Default (14 days x 3 series, 85 DOM nodes) | 5 | **112.2** (107.3 to 112.6) | 48.3 | 149.4 | 68.1 |
| 90 days x 8 series + 400 rows | 3 | **122.2** | 59.0 | 161.9 | 79.5 |
| 365 days x 8 series + 2,000 rows | 3 | **151.4** (128.5 to 152.1) | 83.4 | 191.9 | 105.8 |

Per process, default page: app 70.1 RSS / 19.1 footprint, WebContent 42.1 / 29.2, Networking 10.3 / 4.7, GPU 26.8 / 15.3. Before any WKWebView existed the app was **33.7 MiB RSS / 8.1 footprint** (committed `report-hidden.json`; the three release probes read 33.7 to 33.9 / 8.1 to 8.3) (in-process, bare AppKit accessory app; not the SwiftUI menu-bar spike behind the plan's 45-50 MB).

With a snapshot (default page, 5 runs): in-process right after the snapshot 152.7 app+WebContent RSS; external, sampled about 1 s after the report was written (the 7 s hold is the window it can be sampled in), **140.2** RSS (135.2 to 140.6), footprint 63.0. The snapshot adds **+40 MiB RSS in-process at its peak (110 vs 70 for the app) and +28 MiB externally a second later (97.8 vs 70.1), +14 MiB footprint (33.5 vs 19.1)** to the app process; part of it is released within about a second. The GPU helper's footprint occasionally spikes after a snapshot (14.5 to 58 MiB across runs).

Snapshot on tall pages (one run each, in-process right after the snapshot, 2048x4800 px, PNG 758 to 779 KB): 90 days **238 MiB**, 365 days + 2,000 rows **268 MiB** app+WebContent RSS (footprint 179 and 203).

**Budget check, the plan's "app + WebContent ≤ 180 MB":**
- Steady state: pass in every case tested (worst 152). Reading the row as "every process WebKit spawns" the worst case is 192 MiB RSS and would fail; default is 149.
- `takeSnapshot`: pass for the default page (153), fail for tall pages (238 to 268). Keep snapshots in a QA harness, not in the shipping app.

Closing the canvas (release probe, 3 runs, identical): after the window is closed and the `WKWebView` released, **WebContent and Networking exit within 0.5 s**; **the GPU helper stays until the app exits** (12 s observed); the app stays at **about 72 MiB RSS / 18 footprint** (72.2 to 72.7; once 67.2) instead of returning to 34 / 8. All helpers exit with the app (checked 3 s after exit in all 16 measured runs: none alive). Consequence: the plan's "App idle ≤ 60 MB RSS" budget cannot hold after the first Control Center open if the app is one process.

Measured with a never-shown window on one Apple silicon Mac. A visible window (compositing layers, `requestAnimationFrame` running, retina-scale backing) is not measured and is expected to cost more; check it during WP-41 integration.

### Toolchain and hygiene

- Builds with full Xcode (release `.app` in 6 s warm) and with **Command Line Tools only** (`swift build`, debug; 3 `ld` warnings about missing Developer search paths; the CLT-built binary rendered and passed 17/17 asserts). ## Gotchas for WP-41

1. `WKURLSchemeHandler` is `@MainActor` in the macOS 27 SDK and the handler answers synchronously. If it ever becomes async, every callback needs a "was `stop` called" guard: WebKit raises an ObjC exception (a Swift crash) when `didReceive`/`didFinish` follow `stop`.
2. Use `HTTPURLResponse` (a plain `URLResponse` cannot carry the CSP header). A wrong CSS MIME makes WebKit silently ignore the stylesheet; the resolver pins MIME per extension.
3. `sendBeacon` returns `true` when `connect-src` blocked it: a return value is not evidence of a send; listen for `securitypolicyviolation`.
4. No `connect-src` means the page cannot `fetch` its own scheme either. That is intended: data comes only through arguments.
5. `style-src` does not stop CSSOM: `el.style.x = …`, `style.setProperty` and constructable stylesheets all work; `setAttribute('style')` and `style=""` markup do not. Charts drawn with SVG presentation attributes (`fill=`, 42 rects) work. A "no inline style" rule must be a lint, not a CSP promise.
6. The CI grep for `http(s)://` literals will flag the SVG namespace string in UI code (the spike reads it from an inline `<svg>` instead). Bundled chart libraries will trip it too.
7. After the one allowed entry navigation, **a reload of the canvas is denied** (including `reload()`); the native side must re-arm `entryAllowed` before it calls `load` again (needed for crash recovery).
8. Hidden views: `visibilityState` is `hidden` and `requestAnimationFrame` does not run, but `takeSnapshot(afterScreenUpdates:)` still paints after a settle wait. Golden renders must not depend on rAF or animations.
9. `WKContentRuleList` regexes have no alternation, so each allowed scheme is its own rule. The first draft blocked only `^https?://` and a `ws://` WebSocket got through (caught by the loopback listener). Compile the list into a temp or app-owned store, not the default one under `~/Library/Caches`.
10. WebKit spawns WebContent, Networking and GPU helpers. The GPU helper outlives the web view.

## Not verified

- A visible window (memory, rAF, compositing); dark mode; text rendering fidelity beyond the PNG.
- The real engine payload size or shape; the 365-day page is synthetic.
- An async scheme handler and the `stop` race (`stop` was called 0 times).
- `<script type="module">` as a static tag (only dynamic `import()` was tested); the page is a classic script.
- Content-rule-list compile time and store location in the shipping app.
- Another Mac, another macOS build, an Intel Mac, or a WebKit update.
- What happens to the LaunchServices entry; whether `open -g` ever shows a Dock bounce on other macOS settings (none seen here: `LSUIElement`).

## Reproduce

All builds and tests go through the heavy lock; the CLI runs are light (`nice`) and use a temp `HOME`. From the worktree root, with `H=scripts/dev/heavy.sh` and `S=spikes-tracked/web`:

```sh
$H $S/scripts/spm.sh test                      # 11 XCTest tests
$H sh $S/scripts/build-app.sh                  # release, ad-hoc-signed LSUIElement .app in $S/dist
BIN=$S/dist/WasitmeWebSpike.app/Contents/MacOS/WasitmeWebSpike
sh $S/scripts/run-matrix.sh $BIN $S/web OUT    # 8 variants, prints frontmost app before/after
sh $S/scripts/measure.sh $BIN OUT/mem 5 --no-snapshot        # external ps + footprint on live helpers
python3 $S/scripts/mem-summary.py OUT/mem
sh $S/scripts/launch.sh $BIN --ui-dir $S/web --out-dir OUT --tag 1 --release-probe
sh $S/scripts/open-g.sh $S/dist/WasitmeWebSpike.app OUT openg --placement hidden --settle 3
$H sh $S/scripts/clt-spm.sh build              # Command-Line-Tools-only build
sh $S/scripts/residue.sh                       # names-only ~/Library listing; run before and after
```

Evidence (counts, timings, process names only; no paths, prompts or logs): `spikes-tracked/web/evidence/{matrix,memory,release,openg,tests}`. `memory/memory-summary.txt` is the table above in full.
